# 04: Adapter pi

**What to build:** Prawdziwy agent pi podpięty pod kręgosłup, E2E. Extension w katalogu extensions pi (in-place, poza stow) woła wspólny `agent-hook`: użycie wbudowanego narzędzia `ask` → notify (jedyny moment, gdy pi prosi o input — pi nie ma trybu pozwoleń w tej wersji), `before_agent_start` → working, `agent_settled` → done, `session_shutdown` → clear. Instancje przez `ai pi`. Kluczowe ryzyko do zweryfikowania: jak extension spawnuje proces (agent-hook) i czy PPID-walk z wnętrza procesu pi dociera do PID foot — jeśli nie, udokumentować obejście w Comments. Etykiety sesji: projekt z cwd, etykieta `agent · projekt` ze state file.

## Comments

- **Korekta założenia specu:** pi 0.87.1 **nie ma wbudowanego narzędzia `ask`** (toolset: bash/edit/find/grep/ls/read/write; sprawdzone w binarce i w repo upstream @0.87.1 — założenie z README agent-status nie holds). Obejście zachowujące intencję: extension **rejestruje własne narzędzie `ask`** (TypeBox schema, `executionMode: sequential`) — to czyni je jedynym momentem, gdy pi prosi o input: `tool_call(ask)` → notify (pytanie jako message), `execute` blokuje na dialogu `ctx.ui.input` aż user odpowie, `tool_result(ask)` → working. Bez UI (print/json) tool zwraca fallback „proceed with a sensible default” — notify i tak pali się na `tool_call`, więc ścieżka zdarzeń jest identyczna.
- Mapping zdarzeń: `session_start` → łapanie session id; `before_agent_start` → working; `agent_settled` → done (nie `agent_end` — retries/compaction/queued follow-ups); `session_shutdown` → clear; `tool_call`/`tool_result` tylko dla `ask`. agent-hook wołany `spawnSync` (deterministyczne zakończenie clear przy quit; ms-koszt, nie blokuje agenta sensownie).
- E2E na żywym systemie (Hyprland 0.56 + foot + dunst + waybar): print-mode sekwencje; interactive TUI sterowane wtype (odpowiedź „blue” przez dialog przyszła do modelu — w pliku sesji `ANSWER=blue`); dwa równoległe agenty w tym samym projekcie; click→focus przez `dunstctl action` z otwartym dialogiem ask. Bonus: potwierdzony w prawdziwym dunst replace po stack-tag z ticketa 01 (critical `notify` zastąpiony przez `done` tej samej sesji) — zamyka wątek E2E z 01.
- Znane minora, nie-blokujące: (1) procesy subagentów pi-subagents ładują user extensions → palą własne, krótkożyjące pliki stanu (working→done→clear, ten sam pid foot) — samoczyszczące, bez ryzyka widm; (2) pi uruchomiony bez wrappera `ai` (np. przez SSH jak ta sesja) → pid 0, wpis nieklikalny — zamierzony skutek twardej konwencji `ai` ze specu; (3) `session_shutdown` na `/reload` czyści wpis — nieszkodliwe, agent przy reloadzie i tak idle.
- Testy: adapter celowo bez testów automatycznych (spec: cienkie wrappery, pokryte seamem E2E); istniejący suit `bash agents/tests/test-agents.sh` → ALL PASS (bez zmian).
- **Review (2 równoległe reviewery: Standards + Spec, oba verdict OK):** przyjęta jedna poprawka tekstowa — fallback bez UI przeczył opisowi toola („nie zgaduj” vs „proceed with a sensible default”); teraz fallback każe agencowi zadać pytanie w odpowiedzi zamiast samemu odpowiadać. **Odrzucona poprawka z review (async spawn zamiast spawnSync):** przetestowana E2E i wycofana — async spawn wyściguje `agent_settled`→done z `session_shutdown`→clear (współbieżne dzieci agent-hook nadpisują się w losowej kolejności): clear zdążył przed done → trwały ghost state-file (pid 0, nieprunowalny), a notify przepadał przegrawszy z working. spawnSync jest nośnikiem poprawności: serializuje zdarzenia sesji i gwarantuje clear przed exit — udokumentowane w komentarzu w extension (ponytail: sufit = blokada event loop na runtime agent-hook ~15ms).
